# RYOTA KATADA / PORTFOLIO - Design Document

## 1. Design Concept

"CRT Technical Monitor" -- レトロなブラウン管モニターの技術画面を模したビジュアルの中に、ポートフォリオ情報を配置する。画面中央では自作の3Dモデル(ゲーム機ガジェット)が静かに浮遊・回転し、両脇の情報パネルがハードウェアモニターのステータス表示のように並ぶ。装飾は抑え、情報密度とエフェクトの質感で見せるデザイン。

- 全体: `overflow: hidden` の固定レイアウト。スクロールなし(デスクトップ)
- Virtual Screen: ヘッダー/フッター/左右マージンで囲まれた領域に `1px solid var(--border)` の細い境界線。CRTの表示領域を示す
- マージン: 上下72px、左右64px(1000px以下で上下40px、左右16px)
- フッター中央: 3Dモデルセレクタ(前後ボタン + モデル名 + n/m カウンタ)

## 4. Color Palette

CSSカスタムプロパティで一元管理。ライト/ダークの2テーマを `body.dark-mode` クラスで切り替え、`localStorage`(`portfolio-theme`)に永続化。

切り替えは、ヘッダーの右にある壁の照明スイッチ(`#theme-toggle`)で行う。日本の壁スイッチ(パナソニック WNP5101MWP のような、縦長のプレートの中央に小さな波動スイッチが 1 つ付いたもの)の 3D モデルで、文字のラベルは出さない。波動スイッチは、ライトでは上側が、ダークでは下側が沈む。プレートと波動スイッチの色は、ライトでミルキーホワイト(`#efece4`)、ダークでチャコール(`#242424`)。波動スイッチの右寄りに小さな縦線の目印がある。押す(クリック、タップ、Enter、Space)と、押した側が沈むように 150ms で傾き(少し行き過ぎて戻る)、色も同じ時間で移る。`prefers-reduced-motion` が reduce のときは動かさずに切り替える。モデルの作りと描き方は 7 章の「Theme Switch」。ボタンは、ほかのヘッダーのボタンと同じ高さで、枠と地の色は持たない。スイッチの状態は `body.dark-mode` から決まる(3D も、読み込む前の CSS の絵も)ので、初回描画前にテーマを付けるページでは、最初の表示から状態と配色が合う。支援技術には、`role="switch"`、`aria-checked`(ダークで true)、名前 `Dark mode` で今の状態を伝える。初期のテーマは保存した値だけで決まり、OS の設定(`prefers-color-scheme`)は見ない。

## 5. Typography

| Font | Variable | Usage |
|------|----------|-------|
| Share Tech Mono | `--fp`, `--fm`, `--fh` | 見出し、ローダー、年表、プロジェクト名、モデルセレクタ、ヘッダー(`--fh`)。テクニカルモニター感を演出 |
| Inter 300/400 | body `font-family` | 本文、フッタークレジット。可読性確保 |

`letter-spacing` を広めに取り、技術モニターの疎な表示を再現。

ヘッダーの 1 行は、Share Tech Mono の字幅(0.54em)でちょうど収まるように詰めてある(10. Responsive Behavior)。Web フォントを読み込む前や読み込めなかったときに出る Courier New は字幅が 0.6em あり、ヘッダーの文字がそのぶん広がる。そのため、ヘッダーのフォント `--fh` には、Share Tech Mono の次に `Share Tech Mono Fallback` を置く。これは `style.css` の `@font-face` で、Courier New(ないときは同じ 0.6em の等幅フォント)を `size-adjust` で 89.98% に縮め、字幅を Share Tech Mono にそろえたもの。基本ラテン文字だけに当てるので、Share Tech Mono にない字(← HOME の ←)は、これまでどおり Courier New で出る。Share Tech Mono を読み込んだあとの見た目は変わらない。`size-adjust` に対応しないブラウザ(Safari 16 まで)では、Courier New がそのままの幅で出るが、320px でも 1 行に収まる。

## 6. Visual Effects

### 6.1 Background - Dot Grid

```css
background:
    radial-gradient(circle, var(--grid-dot) 1px, transparent 1px) 0 0 / 24px 24px,
    var(--bg);
```

24pxグリッドで1pxの円形ドットを敷き詰め。方眼紙/エンジニアリングペーパーの質感。

### 6.2 Scanlines

4pxごとに opacity 0.015 の水平線。CRTモニターの走査線を再現。極めて薄く、意識しないと見えないレベル。

### 6.3 Dithering Overlay

4x4pxのチェッカーパターンが10秒かけてゆっくりスライド(`mix-blend-mode: overlay`)。レトロゲーム機のディザリング描画を模倣。

### 6.4 Rendering

- **Tone Mapping:** AgX(フィルム調のソフトなコントラスト)、exposure 1.05
- **Environment:** `RoomEnvironment` を PMREM 化して IBL に使用

## 7. 3D Scene

### Models — ローテーション

自作モデルの GLB を `public/models/meshopt/` に置き、`models.ts` のマニフェストに1行追加するとローテーションに加わる。並びは、本人が触ってきた順にする。

```ts
export const MODELS: ModelDef[] = [
    { path: '/models/meshopt/gbc.glb', label: 'GAME BOY COLOR', fit: 1.35 },
    { path: '/models/meshopt/gbasp.glb', label: 'GAME BOY ADVANCE SP', fit: 1.4, lookUp: CLAMSHELL_LOOK_UP, sink: 0.076 },
    { path: '/models/meshopt/ds.glb', label: 'NINTENDO DS', fit: 1.34, lookUp: CLAMSHELL_LOOK_UP, sink: 0.098 },
    { path: '/models/meshopt/dsi.glb', label: 'NINTENDO DSi', fit: 1.25, lookUp: CLAMSHELL_LOOK_UP, sink: 0.098 },
    { path: '/models/meshopt/3ds.glb', label: 'NINTENDO 3DS', fit: 1.22, lookUp: CLAMSHELL_LOOK_UP, sink: 0.098 },
    { path: '/models/meshopt/psp.glb', label: 'PSP', fit: 1.45 },
];
```

- ページロード時は先頭のゲームボーイカラーを表示する
- フッター中央のセレクタ(◀ / ▶)で手動切り替え。切り替え時はHUDが `LOADING...` 点滅 → 完了後モデル名表示
- `rotationY` で正面補正、`fit` で画面上の大きさを調整(デフォルト 1.5 world units)
- `lookUp` は、そのモデルを表示している間、カメラを通常の角度から注視点のまわりに下へ回す角度(ラジアン)。開いて立てる折りたたみ機(ゲームボーイアドバンス SP、ニンテンドー DS、ニンテンドー DSi、ニンテンドー 3DS)は 12 度(`CLAMSHELL_LOOK_UP`)にして、少し下から見上げる。上画面は手前に約 23 度傾いているので、通常の角度(水平より約 6 度上)からでは縦に詰まって見える。12 度下げると、正面から見た上画面の傾きは視線に対して約 29 度から約 17 度に減り、下画面は約 1 度から約 13 度に増える。下から見るぶん、下半分の面は天井側の明るい映り込みを拾いやすくなり、ダークでは下半分が少し明るくなって、十字キーの上の腕に白い映り込みが出る(10 度でも出る)。ゲームボーイカラーと PSP は `lookUp` を持たず、通常の角度のまま
- `sink` は、モデルを浮かせる高さから下げる量(world units)。下から見ると、回転して横を向いたとき(正面から 60〜70 度)に、手前の上の角が画面の上へ持ち上がる。下げないと、1440×900 で DS の上端は揺れのいちばん上で 26 px まで上がり、枠の上の線(72 px)を越える(下から見る前は 80 px)。上端から下端までの広がりは見上げる前とほとんど変わらず、位置が上にずれるだけなので、縮めずに下げる。値は、1 周と上下の揺れを通した広がりが、1440×900 の枠の上下の真ん中に来るようにした。枠とのあいだは、上下とも SP が約 11 px、DS が約 5 px、DSi が約 29 px、3DS が約 40 px。DS は見上げる前も上 8 px・下 3 px で、もともと枠いっぱいに近い。新しいモデルは自分の `sink` の高さで現れ、角度の移り変わりの途中も枠に収まる
- 低い画面: 枠の上下の帯は px で決まっていて(`--vs-top`、`--vs-bottom`)、モデルは画面の高さに比例するので、画面が低いほど帯の割合が増える。そのため、デスクトップでは、枠が画面の高さに占める割合が 1440×900 のとき(84%)より小さいと、その比だけカメラを引く(`camera.zoom`、`view.ts` の `frameZoom`)。どの高さでも 1440×900 と同じ収まり方になる。1440×900 より高い画面と、1000px 以下の幅でふつうの高さの画面では、`zoom` は 1 のまま。1280×720 では 0.95 倍、1366×768 では 0.97 倍になり、ゲームボーイカラーと PSP も同じだけ小さくなる(この調整の前は、1280×720 でゲームボーイカラーの上端と SP・DS の上下が枠の線にかかっていた)。モバイルは調整しない
- `view.test.ts` は、全モデルを 1 周回し、揺れの上端と下端で、1440×900、1366×768、1280×720、1000×700、1000×480、390×844、320×568 の枠に収まることを確かめる(モバイルは、高さ 48px の固定ヘッダーの下からキャンバスの下まで)。カメラとモデルの置き方の数字は `view.ts` にあり、`main.ts` とテストが同じものを使う
- 切り替え時はスケール 0.85→1.0 のイージングでポップイン。カメラの角度も、同じ速さ(1 フレームに残りの 8%)で新しいモデルの角度へ移る。OrbitControls が持つのは利用者の角度(自動回転、ドラッグとその慣性)で、上下の限界(polar angle の範囲)もそこに当てる。モデルの角度は、毎フレーム、いったん外してから OrbitControls を更新し、その上に重ね直して、限界で切る。そのため、ドラッグや慣性で限界の近くにいても、切り替えて戻すと、切り替えなかったときと同じ角度になる。限界まで寄せたまま折りたたみ機を見ているときは、反対向きのドラッグのはじめの分(最大 12 度)はカメラが動かない。画面の大きさが変わると、カメラは正面に戻り、モデルの角度をその上に重ねる
- 自作のモデルは `scripts/generate-<名前>.ts` が three.js の数式で形を組み、GLB に書き出す。共通の処理は `scripts/model-geometry.ts` にある
- ゲームボーイアドバンス SP は、ヒンジのクリックで止まる約 150 度に開いた形で書き出す。下半分を 7 度だけ後ろに倒して立て(上画面は約 23 度手前に傾く)、`rotationY` なしで正面を向く。下半分をそれ以上上に向けると、ダークで面が天井側の明るい映り込みを拾って白く飛ぶ。`fit` は 1.4 で、1440×900 で上端がゲームボーイカラーとほぼ同じ高さに来る。ゲームボーイカラーと同じ縮尺にすると約 1.57 になり、上端がヘッダーの下の線に届く
- ニンテンドー DS(初代、NTR-001)も、約 150 度に開き、下半分を 7 度後ろに倒して立てる。`fit` は 1.34 で、ゲームボーイアドバンス SP と同じ縮尺になる(開いた高さは DS が約 148 mm、SP が約 155 mm)。1440×900 で、上端は SP より少し下に来る。閉じたとき、上画面の背面側の縁は軸より 3.1 mm 後ろで止めている。それより後ろまで伸ばすと、開く途中で上画面の外側の丸い縁が下半分の面にめり込む
- ニンテンドー DSi(初代、TWL-001、ブラック)も、約 150 度に開き、下半分を 7 度後ろに倒して立てる。`sink` は DS・3DS と同じ 0.098 で、1440×900 の枠とのあいだは上 28 px・下 30 px になる。`fit` は 1.25 で、ゲームボーイアドバンス SP と同じ縮尺になる(最大寸法は開いた高さと幅の約 138 mm)。DS との違いを形に出す: ヒンジは上画面の軸(直径 7.2 mm)が下半分の両端の突起のあいだに入る形で、軸の真ん中に内側のカメラ(つやのある輪の中)とマイク、左の突起の上に 3 つの LED。下半分は電源が十字キーの下の丸いボタン、START/SELECT が A/B/X/Y の下の丸いボタン、右側面に SD カードスロットのふた、左側面に音量ボタン。前の縁はヘッドホン端子だけで、GBA スロットはない。上画面の外側には、閉じたときの手前右に外側のカメラと LED。閉じたとき、上画面のヒンジ側の縁は軸の前 3.9 mm でまっすぐ切り、軸と突起から 0.3 mm 離す。開く途中も軸のまわりを回るだけで、突起にも下半分の面にも当たらない
- PSP(PSP-1000)は板状なので、開かずに正面を向けて書き出す(`rotationY` なし)。いちばん長いのは横幅の 170 mm で、ゲームボーイアドバンス SP と同じ縮尺(`fit` 約 1.54)にすると、2560×1600 で左右のパネルとの間が 20 px ほどしか残らない。`fit` は 1.45 にした(1440×900 で横幅は約 680 px)。本体は前面・銀の中枠・背面の 3 層で、背面は UMD のふたの左右に低いふくらみ(電池ぶたと左のグリップ)がある。全部品が役割を持ち(`scripts/generate-psp.ts`)、面の重なりと開口のふさがりは `model-psp.test.ts` が確かめる
- ニンテンドー 3DS(初代、CTR-001)も、約 150 度に開き、下半分を 7 度後ろに倒して立てる。`fit` は 1.22 で、ゲームボーイアドバンス SP と同じ縮尺になる(最大寸法は幅の約 135 mm)。ヒンジは、上画面の太い軸(直径 9.6 mm)が下半分の両端の突起のあいだに入る形で、軸の下側は面より 2 mm 低い溝に収まる。突起のあいだでは、上画面と軸の円筒が一つの殻になる。画面側の面は円筒の側面に突き当たって折れ目をつくり、外側の面は円筒の下端の線で円筒に接する。突起に向く両側は、円筒の端と同じ平面にそろえた平らな面で、縁の丸みも面取りもない(内側に寄せると、円筒の端とのあいだが開く)。継ぎ目の内側には、上画面の端の面も円筒の面も置かない(殻が透明なので、置くと透けて見える)。`model-3ds.test.ts` は、軸の近くで上画面を表と裏からまっすぐ見通し(両端の際まで)、軸の向きからも両端を見て、隙間や開いた継ぎ目がないことを確かめる。突起の前では、上画面は軸から 6.2 mm で止まる。それより長いと、開いたときに上画面の角が突起の丸い背にめり込む
- 2 つの面が同じ平面で重なると、深度の判定がぶれて三角形状の濃淡が出る(とくに不透明なレンズや液晶と重なるとき)。DS では、くぼみの底を上に載る部品の形に抜くか、部品の底面を省いて、重なりをなくしている。`model-materials.test.ts` が DS の GLB の全三角形で確かめる。DSi も同じ作り方で重なりを 0 組にし、`model-dsi.test.ts` が全三角形で確かめる。ゲームボーイアドバンス SP には同じ重なり(レンズとくぼみの底、液晶とレンズ、十字キーとくぼみの底など)がまだ残る

### Material Treatment

GLB のマテリアルは使わず、部品ごとに `MeshPhysicalMaterial` を割り当て直す(`model-materials.ts`)。色はグレーの濃淡だけで、色相は持たない。

- 役割: GLB のマテリアルが extras に `role` を持つ部品は、その役割の質感になる。役割は 7 つ。ゲームボーイカラー、ゲームボーイアドバンス SP、ニンテンドー DS、ニンテンドー DSi、PSP、ニンテンドー 3DS は全部品に役割を持つ(`scripts/generate-gbc.ts`、`scripts/generate-gbasp.ts`、`scripts/generate-ds.ts`、`scripts/generate-dsi.ts`、`scripts/generate-psp.ts`、`scripts/generate-3ds.ts` が書き出す)。DSi は黒い本体も `shell`(ほかの機種と同じほぼ透明な灰色で、色は持たない)
  - `shell`(本体の成形プラスチック): ほぼ透明な灰色。正面から見ると奥が透け、映り込みの強いところと、輪郭に向かって面が寝るところほど濃くなる。透明な本体でも外形が読める
  - `lens`(画面のレンズ): 黒い印刷を透明なアクリルで覆った面。不透明で、クリアコートの映り込みを強めにする
  - `lcd`(液晶): レンズの窓から見える、艶のない暗い面。クリアコートを持たず、映り込みはレンズだけが持つ。手前のレンズを通して見る面として、視線に対して面が寝るほど暗くする(アクリルの反射率 4% のフレネルで、通る光が減るぶん)。正面ではレンズより少し明るく、回るとレンズが映り込みで明るくなり、液晶は暗くなるので、レンズの奥にあるように見える。DS では下の画面(タッチスクリーン)も `lcd` で、枠より一段下げる
  - `print`(ロゴ、背面のシール、SP と DS の Nintendo バッジと LED。DSi では POWER・START・SELECT の文字、LED とその絵文字、内側のカメラの輪): 艶のない半透明の灰色。部品の上に重なる薄い板なので、表の面だけを描く。SP の底面のシールとバッジは外側の 1 面だけで作り、本体ごしに正面から透けないようにする
  - `button`(十字キー、A/B、音量ダイヤル、電源スイッチ。SP では START/SELECT、ライトのボタン、L/R も硬いボタン。DS では X/Y、POWER、音量のつまみ、タッチペンの頭も。DSi では丸い POWER と START/SELECT、音量ボタン、L/R、タッチペンの頭): 本体より濃い半透明。艶がある
  - `rubber`(GBC の START/SELECT、SP の上画面のネジを隠すゴム、DS と DSi の上画面のゴムと底面の足): `button` と同じ濃さで艶を消し、縁にだけ柔らかい光沢(sheen)
  - `cavity`(ネジ、スピーカー穴、端子や側面の溝の奥、SP のストラップ穴、DSi のカメラの穴とマイク穴、SD カードスロットの奥): 暗く落ちる面。DS のスピーカー穴は 56 個あるので、内壁と奥の面を 1 つの円すいにまとめる(縁は 46 角形のまま)
- `shell`・`button`・`rubber` は、シェーダーの不透明度に、映り込みの明るさと視線に対する面の傾き(フレネル)を足す(`onBeforeCompile`)。描画パスもテクスチャも増やさない。`transmission` は追加の描画パスが要るので使わない
- 役割のない部品: 体積順に3層の半透明(shell / mid / detail)を自動割り当てし、`screen` という名前のメッシュに黒色・クリアコートの画面マテリアルを当てる。いまのモデルはすべての部品が役割を持つので、この割り当ては使われていない
- 全メッシュに `EdgesGeometry` + `LineSegments2` の構造線(主要な可視要素)
- ダークモード時はエッジ色・不透明度・ライト強度を引き上げ。役割の質感もライトとダークで値を持ち、テーマの切り替えに追従する

### Theme Switch

ヘッダーのテーマ切り替え(4. Color Palette)の 3D モデル。`theme-switch-3d.ts` が three.js の数式で組み、GLB は持たない。

- 形(mm): プレート 70 × 120 × 6(縁を 2mm 丸める)。中央の開口は表で 31 × 43、奥は丸めのぶん細い。波動スイッチ 26 × 38 × 5 が中心の軸で傾き、水平のときに表がプレートと同じ面に来る。傾きは 13 度。目印は波動スイッチの右寄りの 1 × 8 の縦線
- 見え方: 正面から少し右上にずれたところから見る(FOV 16)。光は上から強く当て、上を向いた面(出た端、縁の丸め)が光り、下を向いた面は陰になる。正面はほぼ指定の色のまま。ダークでは光を強める(Ambient 2.0 / Key 7、ライトは 2.2 / 2.2)。キーライトの影で、出た端の影が開口に落ちる。ライトでは波動スイッチの面が上を向いて明るく、出た下端の影が下に落ちる。ダークでは面が下を向いて暗く、沈んだ下側から明るい開口の縁がのぞく
- 読み込み: どのページも `theme-switch.ts` を読む(トップ、/things、/hire はそれぞれのバンドルから、/blog と /work は `/theme-switch.js`)。これは、ページの load のあと、空いた時間に `theme-switch-3d.ts` を動的 import する。three.js はそのときに読み込まれる(ビルドの `--splitting` で別のチャンクになり、トップの 3D と同じチャンクを使う)。読み込むまでと、WebGL が使えないとき、読み込めなかったとき、コンテキストを失ったときは、`style.css` が CSS で同じスイッチを描く(プレートが `::before`、波動スイッチと開口が `::after`)。陰の色は `color-mix()` で混ぜずに固定の色で持つ(`--sw-plate-hi` など)。`color-mix()` のない Safari 16.1 までは 3D も読み込めないことがあり、そこでもこの絵が出るようにするためである。`header.test.ts` が、スイッチの規則に `color-mix()` がないことを確かめる3D を描けたら、ボタンに `is-3d` を付けて CSS の絵を消す
- 描画: WebGL のコンテキストはヘッダー用に 1 つ(トップはこれと 3D シーンの 2 つ)。描くのは、最初と、テーマが変わったとき(150ms のあいだだけフレームを回す)と、大きさや画素比が変わったときだけで、ふだんはループしない。テーマはページのスクリプトが持ち、スイッチは `body.dark-mode` の変化を見て動く
- `theme-switch-3d.test.ts` は、ライトで上側、ダークで下側が沈むことと、行き過ぎを含めて傾けても波動スイッチが開口の内側に収まることを確かめる

## 10. Responsive Behavior

| Breakpoint | Changes |
|------------|---------|
| > 1440px | 文字の単位 `--text-u`(通常 1px)を幅に応じて `1 + (100vw - 1440px) × 0.00025`、上限 1.28 まで控えめに拡大する(1920px で 1.12倍、2560px で 1.28倍)。ヘッダー/フッターの帯は変えない。枠の幅 `--frame-w` は「モデル用に空ける帯 `--model-clear`(84vh)+ 両サイドバー」を目安に頭打ちにして中央に置く。これらの値は `style.css` の 1 か所で全ページに設定する。/things、/blog、/work、/hire も文字の単位と枠がトップと同じになり、ページを移ってもヘッダーと枠は動かない。**トップ**: 文字が使わなかった高さは余白に回す: 余白の単位 `--space-u`(通常 1px、上限 2.5)がサイドバーの内側の余白、パネルの間隔と内側の余白、項目の間隔、行間を広げる。サイドバー幅は `--sidebar-w`(230 × `--text-u` + パネルの余白が増えたぶん)。キャンバスは全面のまま。高さの見積もりは `--fit-fixed` / `--fit-lines` / `--fit-space` で持ち、サイドバーが収まらないときは余白、次に文字の拡大を抑える(このときは /things、/blog、/work、/hire の文字も同じだけ抑える)。見積もりの値は両方のサイドバーを測り、高いほうに合わせる。ただし WRITING は除いて測る。入れると、トップだけでなく /things、/blog、/work、/hire の文字も小さくなるためである。いまの値は、PROJECTS があったときの右のサイドバーで測ったもの。PROJECTS を MAKING にして右は低くなり(1440px 幅で 861px から 796px)、WRITING を除くと左(836px)のほうが高くなったが、文字の倍率を変えないように値は据え置いている。その後、WORK の要約をプロジェクトの概要に差し替えて、右は 1440px 幅で 98px 高くなり、WRITING を除いても 861px を超えたが、同じ理由で値は据え置いている(超えたぶんは右のサイドバーのスクロールになる)。見積もりの値は、文字の倍率を下げる向きには変えない。WRITING のぶんも含めて高さが足りないときは、文字も余白も縮めず、サイドバーをスクロールさせる。「おすすめ」の記事が 1 件増えるごとに、スクロールする量も増える。**トップの右のサイドバーの本文**: 右のサイドバー(WORK、MAKING、WRITING、LINKS)では、本文の文字を本文の単位 `--body-u` の倍数にする。本文に当たるのは、項目の説明、技術タグ、記事のタイトルと年月、リンクのラベルである。`--body-u` は `--text-u` と同じ値だが、幅が 1920px を超える画面では、右のサイドバーの中だけ 1.1(`--body-u-max`)で止まる。幅 1920px 以下の画面では、見た目は変わらない。1920×1200 と、横長のルールが当たる 1920×1024 では `--text-u` が 1.12 になるが、本文も 1.12 倍のままである。そのため、幅が 1920px を超えたところで、右のサイドバーの本文は最大 2% ほど小さくなる(1.12 倍から 1.1 倍)。2560×1440 と 2560×1600 では、青い見出しと項目名(`.ph`、`.work-name`、`.project-name`)は 1.28 倍まで大きくなり、本文は 1.1 倍で止まるので、本文の周りに余白ができる。技術タグの行にある `REPO →` は青いが、同じ行の文字と大きさをそろえる。パネルの見出しの行(`ALL →` を含む)、左のサイドバー、ヘッダーとフッターの文字は `--text-u` のまま。/things、/blog、/work、/hire の文字も変えない。`--fit-*` の見積もりは変えないので、本文が小さくなったぶん、右のサイドバーのスクロールが減る。**/things、/blog、/work、/hire**: 文字だけでなく余白(枠の内側、グリッドの間隔、カードやシートの内側)も `--text-u` の倍数にして、1440px のときの見た目をそのまま拡大する。`--space-u` は使わない。サイドバーの高さの余りを配る単位で、縦にスクロールするページには当てはまらないためである。罫線と枠の角の目印は拡大しない |
| > 1440px かつ横長(15:8 以上) | 高さが足りないぶん横幅を使う。サイドバーを 340 × `--text-u`(+ 余白ぶん)に広げ、SKILLS は2列(名前の下にバー)、CAREER は年を役職の横に置く |
| 1000-1440px | フルレイアウト。サイドバー230px、マージン64px/72px。画面の高さが足りないときは、サイドバーの中が縦にスクロールする(8. Information Panels)。右は高さ 1465px ほど(「おすすめ」の記事 1 件ごとに 45px ほど増える)、左は 990px ほどを下回るとスクロールする |
| 768-1000px | サイドバー120px、マージン16px/40px、フォントサイズ縮小 |
| < 768px | 縦スクロール。ヘッダー固定 + 3Dキャンバス(60vh)+ モデルセレクタ + パネル群(WORK を全幅 → SKILLS/LINKS 2カラム → CAREER → MAKING → WRITING を全幅)+ フッター。ヘッダーのボタンは 768-1000px と同じ 12px・高さ 30px の枠のまま、タップできる範囲を高さ 44px まで広げる(幅も 44px 以上、ボタンの間隔は 8px)。480px 以下と 360px 未満では、ロゴと1行に収まるように、ボタンの左右の余白と字間を段階的に詰める。テーマのスイッチは幅 26px(768-1000px と同じ高さ 30px に合わせて縮む)で、タップできる範囲はほかのボタンと同じく 44px 四方。480px 以下では、ヘッダーの左右の余白をどのページも 12px にする。ロゴは 20px・字間 2px。480px 以下ではボタンが空けた幅に合わせて幅に比例させ、360px で 16px・字間 1px、390px で 18px・字間 2px、420px 以上で 20px にする(345px 以下は 15px・字間 1px) |

## 11. /things Page

好きなモノを並べる別ページ。トップと同じ CRT モニターの言語(ドットグリッド、スキャンライン、ディザ、`.panel`、Share Tech Mono)を使い、3D シーンは持たない。

- グリッド: 1 カラム(〜640px)/ 2 カラム(640px〜)/ 3 カラム(1100px〜)
- 大きい画面: 1440px を超えると、文字と余白をトップの文字と同じ倍率で拡大し、枠をトップと同じ幅で中央に置く(10. Responsive Behavior)

## 12. /blog Pages

microCMS で書いた記事の一覧(`/blog`)、記事ページ(`/blog/<記事ID>`)、RSS(`/blog/feed.xml`)。/things と同じ CRT モニターの言語を使い、3D シーンは持たない。記事ページは本文の読みやすさを優先する。

- レイアウト: ヘッダー、仮想スクリーン枠、フッターは /things と同じ。ページ全体が縦スクロール。ヘッダー左の `BLOG` は `/blog` へのリンク。大きい画面では /things と同じく、文字と余白を拡大し、枠をトップと同じ幅で中央に置く
- 一覧: グリッドは /things と同じ 1 / 2 / 3 カラム。カード(`.post`)は `.panel` を継承し、アイキャッチ → カテゴリタグ + 公開日 → タイトル(→)→ 概要(3 行まで)→ タグ。カード全体が記事へのリンク。アイキャッチは /things の写真と同じく、カードの左右の端まで広げ、下に区切り線を引く。枠の比率は 1200:630 で、画像の比率が違うときは中央を切り抜いて枠を埋める。アイキャッチがない記事も同じ枠を残し、ページ色の地に `NO SIGNAL` と出す。こうすると、同じ行のカードで文字の位置がそろう
- 記事: 枠の中央に最大幅 800px のシート(`.article`)を置き、その中に幅 720px の本文を置く。シートは `.panel` の色を不透明にしたもので、長い本文の背後にドットグリッドが出ない。アイキャッチがある記事は、シートの上端に左右の端まで 1200:630 で置き、その下にカテゴリ、日付、タイトルを続ける。アイキャッチがない記事には何も置かない。下に前後の記事へのリンクを置く
- 文字: タイトルは Share Tech Mono。本文は Inter 16px、行間 1.9 で、1 行は全角 43 文字前後。1440px を超える画面では、文字もシートと本文の幅も同じ倍率で広がるので、1 行の文字数は変わらない。本文中の見出しは Inter 600 で、h2 に四角のマーカーと下線、h3 に左のアクセント線(CAREER と同じ)を付ける。どちらのフォントにも日本語のグリフがないので、日本語に使うゴシック体を `--font-ja` で指定する
- コード: ビルド時に Shiki で色を付ける。色は `--code-*` の CSS 変数で持つので、ライト/ダークを切り替えるとコードの色も変わる。ファイル名と言語はブロック上部のバーに出す
- 画像: microCMS の画像 API で AVIF と WebP を作り、`<picture>` で出す。AVIF に対応したブラウザは AVIF を、それ以外のブラウザは WebP を読み込む。幅は `srcset` で出し分ける。本文は 720px、1080px、1440px(本文幅の 1 倍、1.5 倍、2 倍)、アイキャッチは一覧のカードで 400px、600px、800px、記事で 800px、1200px、1600px。`sizes` には、表示される幅を、余白が変わる画面幅の区切りごとに書く。1440px を超える画面では、本文と記事のアイキャッチが文字とともに広がるので、広がりきったときの幅(本文 922px、アイキャッチ 1024px)を書く。この倍率の上限は `blog/article.ts` の `WIDE_SCALE` で持ち、`style.css` の `--text-u-max` とそろえる。一覧のカードは、枠が狭まるぶん実際より大きめの幅になるが、1440px 以下と同じ式のままにしている。元の幅より大きくはしない。画像 API は、元より大きい幅を指定すると拡大した画像を返すためである。`width` と `height` を付けて、読み込む前から枠の高さを決めておく。`<picture>` は `display: contents` でボックスを作らず、`<img>` だけのときと同じ配置にする。アイキャッチの alt は記事のタイトルにする
- 画像を読み込む順: 記事のアイキャッチは最初の画面に入るので遅延させず、`fetchpriority="high"` を付ける。アイキャッチがない記事では、本文の最初の画像を遅延させず、`fetchpriority="high"` を付ける。元の HTML に `loading="lazy"` があっても外す。本文のほかの画像は `loading="lazy"`。一覧では、多くの画面で最初に見える 6 枚(3 列なら 2 行、2 列なら 3 行)を遅延させず、1 枚目に `fetchpriority="high"` を付ける。7 枚目からは `loading="lazy"`
- 共有: 記事ページの `og:image` と `twitter:image` にアイキャッチを使う。どのサービスでも表示できる JPEG にして、幅は 1200px までに縮める。600×315 以上なら `twitter:card` を `summary_large_image` に、それより小さければ `summary` にする。小さい画像を大きいカードに引き伸ばさないためである。アイキャッチがない記事と一覧には付けない
- リンク: 外部サイトは別タブで開く。旧ブログ(kissa-katada.com)の記事へのリンクは `/blog/<記事ID>` に書き換える
- データ: ビルド時に microCMS の `blogs` API から全記事を取得する(`blog/microcms.ts`)。認証情報は `MICROCMS_SERVICE_DOMAIN` と `MICROCMS_API_KEY` で、手元では `.env` に、デプロイのワークフローでは GitHub Secrets に置く。ブラウザにも Worker にも渡さない。どちらかがないときや記事を取得できないときは、手元でも GitHub Actions でもビルドがエラーで止まる。GitHub Actions ではデプロイもしないので、本番の `/blog` は前回のまま残る
- 更新: microCMS で記事を公開・更新・公開終了・削除すると、Webhook(`repository_dispatch`)でデプロイのワークフローが起動する(`docs/DEPLOY.md`)
- 生成: `blog/build.ts` が `dist/blog.html`、`dist/blog/<記事ID>.html`、`dist/blog/feed.xml`、`dist/blog.css` を書き出し、`dist/index.html` の WRITING に「おすすめ」の記事を書き込む(8 章)。そのため、ビルドはページをバンドルしてからブログを生成する。`blog.css` は `style.css` を取り込んだ 1 ファイル。ページは静的 HTML で、スクリプトはテーマ切り替え(インラインのスクリプトと、3D のスイッチを読み込む `/theme-switch.js`)だけ
- アイキャッチ: microCMS の `eyecatch` が空の記事には、ビルドが画像を作って登録する(`blog/eyecatch.ts`)。画像は 1200×630 で、文字は入れない。絵柄はマーブル模様。濃淡の帯が、画面を横切る流れに沿って何層にも重なり、一部の帯の縁にアクセント色と、紙の白の細い線が入る。地の色は、墨色から紙の白(`--bg` の `#f5f5f5`)までのなめらかな階調で、中間だけが青い。この青は `--accent`(`#3b82f6`)と同じ色相で、彩度を 3 分の 1 ほどに落としてある。青く見える部分は、平均で画像の半分ほどになる。アクセントはアンバー(`#e3a03a`)とコーラル(`#dd6650`)の 2 色で、`design-tokens.css` の warning と error の彩度を落とした色。1 枚に使うのは 1 色か 2 色。3px 四方の点を 400×210 個並べて描き、点ごとに明るさを最大で ±18(255 段階のうち)ずらして、フィルムのような粒状感を出す。アクセントの縁も、点の単位でまばらになって消える。記事 ID を乱数の種にするので、粒の出方も含めて、同じ記事はいつも同じ絵になる
- アイキャッチの登録: 作った画像を microCMS のメディアにアップロードし(マネジメント API)、その記事の `eyecatch` に登録する(`blogs` の PATCH)。登録できた画像は、同じビルドで書き出す一覧と記事ページにも出す。ビルドが microCMS に書き込むのは、このアップロードと登録だけで、専用のキー `MICROCMS_WRITE_API_KEY` を使う。このキーも、手元では `.env` に、デプロイのワークフローでは GitHub Secrets に置く。キーがないときは、画像の生成も登録もせずにビルドを続ける。`eyecatch` がある記事には書き込まない。一覧を取得したあとに人が設定したアイキャッチも上書きしないように、アップロードの直前と PATCH の直前に、その記事を取得し直して確かめる。この取得は毎回、過去に一度も使っていない URL で行う。絞り込み条件を「作成日時が、乱数で決めた過去の日時より後で、乱数で決めた遠い未来の日時より前」にして URL を変える。この条件はどの記事にも当てはまる。microCMS の CDN は同じ URL への応答をキャッシュするので、前のビルドや並行するビルドのときの古い応答で判断しないためである。microCMS には条件付きの更新がないので、最後の確認から PATCH までの一瞬に設定されたアイキャッチは上書きされうる。書き込みに失敗するとビルドはエラーで止まり、次のビルドは `eyecatch` が空のまま残った記事から続ける。microCMS はこの登録を記事の改訂として扱う。登録した日が公開日と違うと、次のビルドから記事ページの UPDATED にその日が出る。`bun run eyecatch:dry-run` は、microCMS に書き込まずに同じ画像を `out/eyecatch/` に書き出す。記事 ID を引数に渡すと、認証情報がなくても動く
- 開発: `bun run dev` は同じファイルをリクエストのたびに描画する(`blog/dev.ts`)。microCMS から取得した記事は 60 秒間キャッシュする
- テーマ: `localStorage` の `portfolio-theme` をほかのページと共有する
- 配信: Cloudflare Workers の assets が `/blog` を `blog.html` に、`/blog/<記事ID>` を `blog/<記事ID>.html` に解決する

## 13. /work Pages

仕事の事例の一覧(`/work`)と、事例ごとのページ(`/work/<名前>`)。/blog と同じ CRT モニターの言語を使い、3D シーンは持たない。

- レイアウト: ヘッダー、仮想スクリーン枠、フッターは /blog と同じ。ページ全体が縦スクロール。ヘッダー左の `WORK` は `/work` へのリンク。大きい画面では /blog と同じく、文字と余白を拡大し、枠をトップと同じ幅で中央に置く
- 一覧: 枠の中央に、記事のシートと同じ最大幅 800px の列を置く。列の中に事例のカード(`.case`)を並べ、その下に「この2件を支えているボット運用」の節をシートで置く。カードは `.panel` を継承し、`CASE 01` のタグ → タイトル(→)→ 要約。カード全体が事例のページへのリンク。グリッドは 1 カラム(〜640px)/ 2 カラム(640px〜)
- 事例のページ: /blog の記事と同じシート(`.sheet`)に、`CASE 01` のタグとタイトルを置き、本文は「先方の困りごと」「やったこと」「いまどうなったか」の 3 節。本文の組み方(Inter 16px、行間 1.9、幅 720px、h2 に四角のマーカーと下線)も記事と同じ。下に前後の事例へのリンクを置く
- 文章: 確認済みの原稿のとおりにする。原稿から変えるのは、「本人」を「私」にすることと、事例を見出しの名前(大手人材会社向けの人材紹介データベース、ベンチャーキャピタル向けCRM)で呼ぶことだけ。客先名と客先のシステム名は出さない。カードの要約は本文の一節ではなく、本人が決めたプロジェクトの概要の文を一字も変えずに使う。事例のページの `description` にも使う
- データ: `work/cases.ts` の `CASES` に事例を、`OPERATIONS` にボット運用の節を持つ。事例を 1 件足すと、一覧のカードとページが増える。トップの WORK パネル(8. Information Panels)は `index.html` に手で足す
- 生成: `work/build.ts` が `dist/work.html`、`dist/work/<名前>.html`、`dist/work.css` を書き出す。`work.css` は `style.css` を取り込んだ 1 ファイル。ページは静的 HTML で、スクリプトはテーマ切り替え(インラインのスクリプトと、3D のスイッチを読み込む `/theme-switch.js`)だけ
- 開発: `bun run dev` は同じファイルをリクエストのたびに描画する(`work/site.ts`)
- テーマ: `localStorage` の `portfolio-theme` をほかのページと共有する
- 配信: Cloudflare Workers の assets が `/work` を `work.html` に、`/work/<名前>` を `work/<名前>.html` に解決する。/blog と同じ仕組みなので、`worker.ts` と `wrangler.jsonc` は変えていない

## 15. 404 Page

ファイルのないパスを開いたときに出るページ。/work と同じ CRT モニターの言語を使い、3D シーンは持たない。

- レイアウト: ヘッダー(左は `RYOTA KATADA / 404`、右側はテーマのスイッチ / ← HOME / BLOG)、仮想スクリーン枠、フッターは /work と同じ。大きい画面では /things、/blog、/work、/hire と同じく、文字と余白を拡大し、枠をトップと同じ幅で中央に置く
- 中身: 枠の中央に、`NO SIGNAL`(/blog の、アイキャッチのないカードと同じ表記)、大きな `404`(Share Tech Mono)、「お探しのページは見つかりませんでした。」、開いたパス(`URL /…`)を縦に並べる。その下の `.panel`(PAGES)に、HOME、WORK、BLOG、THINGS、HIRE へのリンクを `.link-row` で置く
- パス: ページのスクリプトが `location.pathname` を読み、文字として入れる。日本語のパスは読める形に戻す。長いパスはどこでも折り返す。スクリプトが動かないときは、この行を出さない
- 検索: `noindex` を付け、`canonical` と OGP は付けない
- 生成: `not-found/build.ts` が `dist/404.html` と `dist/not-found.css` を書き出す。`not-found.css` は `style.css` を取り込んだ 1 ファイル。このページはどの深さの URL でも出るので、CSS、スクリプト、アイコンへの参照は、すべて `/` から始まる絶対パスにしている(`bun build` で HTML を書き出すと相対パスになるため、/work と同じく TypeScript で書き出す)。ページは静的 HTML で、スクリプトはテーマ切り替え(インラインのスクリプトと、3D のスイッチを読み込む `/theme-switch.js`)とパスの表示だけ
- 開発: `bun run dev` は、どのルートにも当たらないパスと、ない記事・事例に、このページをステータス 404 で返す(`not-found/page.ts`)
- テーマ: `localStorage` の `portfolio-theme` をほかのページと共有する
- 配信: `wrangler.jsonc` の `assets.not_found_handling` を `404-page` にしている。Cloudflare Workers の assets は、ファイルのないパスに `dist/404.html` をステータス 404 で返す。Worker を先に動かしていても(`run_worker_first`)、assets のバインディングがこの設定に従う。`/models/` の下などでファイルがないときも、このページが 404 で返る。`/404` を直接開くと、同じページが 200 で返る
- 計測: Worker は、このページの閲覧をパス `not_found` として記録する(`docs/ANALYTICS.md`)
